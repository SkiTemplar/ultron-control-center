# v15.0b — Token Diet: skill-vault + Qdrant lazy-loading + MCP token audit

## Problema (diagnóstico 2026-05-12)

Una sesión ULTRON arranca con **~56k tokens fijos** antes de escribir nada:

| Categoría        | Tokens | Causa                                                        |
|------------------|-------:|--------------------------------------------------------------|
| Skills           | 33.8k  | metadata (`name`+`description`) de **las 380 skills** en `~/.claude/skills/` |
| System prompt    |  9.9k  | harness + tool descriptions + bloques "MCP server instructions" (Figma, Supabase, Uber Eats) + lista de ~200 deferred MCP tools |
| Memory files     |  7.4k  | CLAUDE.md global + CLAUDE.md proyecto + MEMORY.md + context.md + SYSTEM-MAP.md |
| Custom agents    |  5.1k  | ~14 agentes (pr-review-toolkit ×6, feature-dev ×3, agent-skills ×3, ultron-* ×5, Explore, Plan, claude-code-guide) |

**La causa raíz es Skills (33.8k).** Claude Code carga la metadata de *todas* las skills instaladas en *cada* sesión — es comportamiento de plataforma. Los hooks (`skill_integrity_check`, `routing-telemetry`, `prompt-feedback-capture`) sólo disparan al **invocar** una skill, no al cargar su metadata. Por eso el sistema de scripts/hooks nunca pudo evitarlo: ataca el punto equivocado.

De las 380 skills, sólo ~25-30 son de ULTRON (personas + core). Las otras ~350 entraron en instalaciones masivas de marketplaces:
- `wshobson/agents` (`claude-code-workflows`) → ~100+ skills dev (`backend-developer`, `python-pro`, `golang-pro`, `rust-engineer`…)
- pack bioinformática → ~80+ (`scanpy`, `anndata`, `biopython`, `deepchem`, `qiskit`, `rdkit`, `pysam`…)
- pack académico → `academic-deep-research`, `academic-pipeline`, `paper-*`…
- scanners blockchain, `agent-skills`@addy (~25), etc.

380 × ~90 tok ≈ 34k. Cuadra con el medidor.

El item antiguo `ultron-arranque-ligero-reducir-overhead-6k-2k-toke` sólo atacaba SKILL.md + CLAUDE.md + MEMORY.md (~6k) — 5× más pequeño que el problema real. **Este spec lo supersede y lo absorbe.**

## Decisiones de USER (2026-05-12)

1. **Skills**: mantener activas las skills realmente usadas (las de "carpetas potentes"); el resto se accede vía **Qdrant** ("como el sistema actual debería hacer ya"). Es decir: lazy-loading real respaldado por el índice semántico.
2. **Keep-list orientativa**: principalmente skills **de código**; algunas de **investigación / académicas**; **finanzas**. Científicas (bio/quantum) → menos, al vault. Personas ULTRON + superpowers core siempre activas.
3. **Telemetría de skills**: cada vez que se lanza una skill → reforzar / incrementar una estadística para ver qué skills predominan; **mergear skills similares**.
4. **MCP**: no quitarlos del registro, pero **no deben gastar tokens** si no se usan. Investigar si se puede tener un server MCP registrado-pero-inactivo (sin volcar deferred tool-names + instruction blocks al contexto); si no es nativo, un toggle.

## Objetivo medible

- Skills: 33.8k → **<8k** (≈40-50 skills activas).
- Overhead fijo total: ~56k → **<22k**.
- Sin pérdida funcional: cualquier skill vaulteada se localiza por Qdrant y se restaura on-demand en <1 turno.

## Workstreams

### WS1 — Skill vault + restore (núcleo)
- `~/.ultron/skill-vault/<name>/` ← destino de las skills no activas (mover, no copiar; preservar `SKILL.md` + assets).
- `~/.ultron/skill-vault/INDEX.json` ← {name, description, tags, source-marketplace, vaulted_at, usage_count}.
- Index Qdrant `ultron_skills`: 1 punto por skill (activa o vaulteada), payload = metadata, vector = embedding de `name + description + tags`.
- `ultron skills vault add <name…>` / `restore <name…>` / `list [--active|--vaulted]` / `search "<query>"` (Qdrant top-k).
- Restore = symlink/copy de `skill-vault/<name>` → `~/.claude/skills/<name>` (válido en la sesión siguiente; Claude Code no recarga skills mid-session, así que el restore avisa "reinicia sesión o ya disponible en la próxima").
- Router (ULTRON skill / context_primer): cuando la query del usuario no matchea ninguna skill activa, query Qdrant `ultron_skills` → si hit fuerte de una vaulteada, surfacearla ("hay una skill `X` en el vault que encaja — `ultron skills restore X`").

### WS3 — Telemetría + ranking + merge
- Extender `routing-telemetry.py` (ya PostToolUse en `Skill|Agent`): por cada invocación → `usage_count++`, `last_used`, `n_sessions`. Persistir en `~/.ultron/telemetry/skill-usage.json` y replicar a payload Qdrant.
- `ultron skills stats` → tabla ordenada por uso; marca "cold" (0 usos en 60d) y "hot vaulted" (vaulteada pero buscada/restaurada ≥3 veces).
- `ultron skills merge-candidates` → para cada par activo, similitud coseno de embeddings en Qdrant > 0.92 → candidato a merge; reporte para revisión manual.
- Política de mantenimiento (mensual, vía `consolidate-memory` o `doctor`): proponer demote de cold activas / promote de hot vaulted / merge de duplicadas.

### WS5 — Quick wins de overhead restante
- SessionStart hook (`session-init.ps1`): **no inyectar el cuerpo completo de `using-superpowers`** (~1.5k cada sesión); el contenido ya está en la skill — basta un puntero de 1 línea.
- Trim `CLAUDE.md` global (revisar solapamiento con `ultron/SKILL.md`), `SYSTEM-MAP.md`, `MEMORY.md` (ya bajó 990→463).
- Auditar `~/.claude/agents/` y plugins que aportan agentes: ¿valen los 5.1k? Candidatos a quitar: `pr-review-toolkit` (6 agentes), `feature-dev` (3) si no se usan.

### WS6 — Consolidación del registro de skills
Hoy hay **4 fuentes de verdad** sobre skills (`skills-registry.json`, `skill-provenance.json`, `skills.manifest.yaml`, `skill-graph.py` + el índice `L1-skills` con 380 entradas en `brain_index`). Ninguna gobierna qué se carga.
- Unificar en **un solo registro** (`~/.ultron/skills/registry.json`) con: `name`, `state` (active|vaulted), `source` (marketplace|local|ultron-core), `tags`, `usage_count`, `last_used`, `n_sessions`, `vaulted_at`, `embedding_id`.
- `registry_sync.py` pasa a ser el único escritor; los otros 3 ficheros → views derivadas o deprecadas.
- `brain_index` deja de indexar las 380 SKILL.md como notas L1 (ruido en FTS5); el registro las cubre.
- `ultron skills doctor` → detecta drift entre `~/.claude/skills/` real y el registro, huérfanos, duplicados.

### WS7 — Qdrant: poblarlo, auto-mejorar embeddings, verificar el pipeline de memoria
**Hallazgo 2026-05-12: `~/.ultron/qdrant_storage` está VACÍO (0 bytes), Docker apagado.** La "capa semántica" de ULTRON no existe todavía — sólo funciona `brain_index` (FTS5/BM25, 26 MB, 733 notas, 10 824 chunks, 1.48 M tokens). Esto es exactamente por qué "no llega a lo que quieres". Este WS se ejecuta **emparejado con el item `memoria-automatizada-qdrant`** (ese item construye el pipeline; aquí lo verificamos y lo auto-mejoramos).
- **Verificar escritura de memoria**: ¿el hook `Stop` (`stop-memory-sync.ps1` + `session-log.py`) está capturando *todas* las sesiones, incluidas las de otras ventanas Claude Code en paralelo? Auditar `~/.ultron/sessions/` (últimas entradas: 2026-04-27/28 — sospechoso) vs `last-stop-sync.json`. Si hay sesiones perdidas → arreglar el hook o añadir un `session-reaper` que barra los transcripts de `~/.claude/projects/*/` no procesados.
- **Poblar Qdrant**: backfill de las 733 notas de `brain_index` + 258 entradas L2-vault + archive → colección `ultron_memory` (chunks de ~512 tok, embeddings locales — `bge-small`/`nomic-embed` vía Ollama o `fastembed` para no gastar API).
- **Búsqueda híbrida**: `ultron recall "<query>"` = FTS5 BM25 + Qdrant cosine, re-rank fusionado (RRF). Scripts simples, sin tocar el contexto: gigas de memoria viven en disco, se traen sólo los top-k relevantes al turno.
- **Auto-mejora de embeddings**: telemetría de recall (qué chunks se recuperan y si la respuesta los usó — ya hay `track-knowledge-reads.py`). Periódicamente: re-embed de notas con modelo nuevo si mejora; detección de notas casi-duplicadas (cos > 0.95) → merge; notas nunca recuperadas en 90d → mover a `archive/` (sigue indexada pero fuera del hot set).
- **`ultron_skills`** (de WS1) y `ultron_memory` comparten el mismo backend y el mismo embedder → un solo servicio.

## Criterio de DONE
1. `~/.claude/skills/` tiene ≤50 carpetas; el medidor de contexto muestra Skills <8k.
2. `ultron skills search "<tema>"` devuelve la skill vaulteada correcta; `ultron skills restore <name>` la reactiva.
3. `ultron skills stats` muestra usage_count real alimentado por el hook.
4. MCP: medido el coste; aplicada la mejor opción disponible (disabled-registered o toggle).
5. SessionStart ya no inyecta el cuerpo de `using-superpowers`.
6. Overhead fijo total medido <22k. Documentado en SYSTEM-MAP § VERSION DRIFT.
7. Un solo registro de skills (`~/.ultron/skills/registry.json`); los otros 3 ficheros = views o deprecados; `ultron skills doctor` sin drift.
8. `qdrant_storage` poblado (≥733 notas backfilled); `ultron recall "<query>"` devuelve resultados híbridos FTS5+Qdrant; Docker+Qdrant verificados live.
9. Verificado que el hook `Stop` captura todas las sesiones (incluidas paralelas); si no, `session-reaper` añadido.

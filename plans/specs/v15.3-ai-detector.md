# v15.3 AI Text Detector — Spec

A local-first skill that estimates whether a piece of text was written by an
LLM. Built as the inverse of the existing `humanizer` skill. Honest by
construction: it reports a confidence band, not a verdict, and degrades
gracefully on text that has been hand-edited or run through the humanizer.

## 1. Problem

Three concrete reasons the user wants this:

- **Counterpoint to `humanizer`.** The humanizer skill removes AI tells. The
  detector is the same patterns read in reverse, so the author can sanity-check
  whether their own output still "smells like a model" before publishing.
- **Academic and professional contexts.** When the user pastes notes that came
  out of a Claude session into a document that will be reviewed by a human (a
  thesis supervisor, an editor, a client), it is useful to know which
  paragraphs still read as generated and which have been rewritten enough to
  pass casual inspection.
- **Self-check before submitting written work.** Newsletter drafts, blog posts,
  PR descriptions, README sections — anything where the user wants to ship
  prose that does not look like it came straight out of an assistant.

Problems this explicitly does NOT solve:

- **Forensic-grade detection.** As of 2026, no public detector can reliably
  distinguish a careful human writer from a competent LLM in a single short
  sample. Watermarking schemes (Aaronson 2023, Kirchenbauer et al. 2023) only
  work when the generating model cooperates, and none of Claude / GPT / Gemini
  ship watermarks for users at the time this spec is written.
- **Real-time scoring of streaming text.** The skill operates on snapshots, not
  on a live editor buffer.
- **Provenance attribution.** "Was this written by Claude vs. GPT-4 vs.
  Gemini?" is out of scope. The skill answers the binary "human-ish vs.
  model-ish" question only.

## 2. Non-Goals

- Any claim of 100 % accuracy. The output is always a probability band with an
  honest disclaimer.
- A commercial AI-detection service competitor (GPTZero, Originality.ai,
  Turnitin AI). Those have a different cost model and far more training data.
- Plagiarism detection. Different problem, different corpora, different
  liability surface. The skill should refuse and point at existing tools if
  the user asks for it.
- Catching hand-edited AI text or text run through the ULTRON `humanizer`
  skill. Performance on such inputs is expected to be poor; the spec accepts
  that and demands the output say so out loud rather than guess.
- Image / audio / video deepfake detection. Text only.

## 3. Constraints

- **Subscription-only.** No `GPTZERO_API_KEY`, no `ORIGINALITY_API_KEY`, no
  paid third-party detection APIs. Same rule as v15.2: ULTRON code never
  reaches for a paid AI endpoint behind the user's back.
- **Local inference where possible.** Use the small-model patterns already
  documented for ULTRON: `dolphin-*`, `qwen-*`, `phi-*` families via a Python
  sidecar. The detector must be runnable with the laptop offline; Layer 2
  (Claude review pass) is opt-in.
- **Multi-signal confidence.** No single feature decides the score. The MVP
  combines at least five orthogonal signals (perplexity, burstiness, sentence
  length variance, type-token ratio, inverted humanizer pattern matcher) so
  that any one of them being wrong does not flip the verdict.
- **Spanish + English coverage.** Same bilingual constraint as the rest of
  ULTRON. Perplexity model and pattern dictionaries must cover both, even if
  Spanish accuracy lags English (Success Criteria §7 codifies the gap).
- **No persistent storage by default.** Pasted text is held in memory for the
  duration of the analysis and discarded. Opt-in `--save` flag for users who
  want trend analysis across many checks.
- **No network egress except Layer 2.** Layer 1 must work fully offline. If
  the user enables Layer 2 (Claude pass), that call goes through the existing
  `claude` CLI subscription path, never a raw API key.

## 4. Inputs

- **The text to analyze.** Three input modes:
  - Paste as a string argument.
  - File path (`--file path/to/text.md`).
  - Stdin (pipe-friendly, for shell users).
- **Optional: known author samples.** A directory or file containing past
  writing by the same author. Used by the stylometric layer to compute a
  baseline distance. Without samples, the stylometric signal is skipped and
  the aggregate score is recomputed.
- **Optional: domain hint.** One of `academic`, `casual`, `journalistic`,
  `technical`, `creative`. Adjusts the perplexity normalization (academic
  prose is naturally less burst-y than casual prose) and the weights of the
  pattern matcher.
- **Optional: target language.** `en`, `es`, or `auto` (the default, via
  `langdetect` or `fasttext-lid`).

## 5. MVP — what MUST be in v15.3.0

### Layer 1 detection signals (all local, all fast)

All five required. None individually decides the output; the aggregator
combines them.

1. **Perplexity scoring.** Run the input through a small local language model
   and compute the mean per-token negative log-likelihood. Lower perplexity
   correlates loosely with model-generated text (Mitchell et al. 2023,
   DetectGPT). Candidate models: `gpt2-small` (~125 M params, fast on CPU),
   `distilgpt2`, or `phi-3-mini` for Spanish. Reported as a z-score against
   a domain-conditional reference distribution.
2. **Burstiness analysis.** Variance of sentence-level perplexity across the
   document. Human writing tends to be burstier (some sentences are very
   surprising, some are filler); LLM output tends toward a flat mid-range.
3. **Sentence-length variance.** Standard deviation of sentence lengths in
   tokens. LLM output clusters around the genre median; human writing has a
   wider distribution.
4. **Vocabulary richness.** Type-token ratio (TTR) and Yule's K, computed on
   lemmatized text via `spaCy` (`en_core_web_sm`, `es_core_news_sm`).
5. **Inverted humanizer pattern matcher.** Take the 29 pattern categories from
   `~/.claude/skills/humanizer/SKILL.md` (em-dash overuse, rule of three,
   inflated significance, copula avoidance, -ing endings, hyphenated word
   pairs, "let's dive in", etc.) and run them as detectors instead of
   rewriters. Each category contributes a normalized hit-rate to the score.
   This is the cheapest and most explainable signal, and the most easily
   defeated by anyone who has read the humanizer skill — which the output
   must acknowledge.

### Layer 2 signals (optional, costs subscription quota)

Off by default. Enabled with `--deep` or via skill settings.

6. **Claude review pass.** Send the text to the `claude` CLI with a fixed
   prompt: *"On a scale of 0-100, how likely is this text AI-generated?
   Briefly explain. Be honest if you cannot tell."* Parse the score and
   reasoning into the report. Roughly 2 K tokens per check.
7. **Stylometric comparison.** Cosine distance between the input and the
   provided author-sample corpus over a 50-feature stylometric vector (mean
   sentence length, comma-per-sentence rate, function-word frequencies, etc.,
   in the tradition of Burrows' Delta). Only runs when the user supplies
   samples.

### Output

A markdown report with:

- A single headline confidence band: `low (0-30 %)`, `mixed (30-70 %)`,
  `high (70-100 %)`. The MVP intentionally refuses to print a single decimal
  number as the headline, to avoid false precision.
- A per-signal breakdown table: signal name, raw value, normalized score,
  interpretation.
- Specific phrases flagged by the pattern matcher, with byte offsets so a
  future UI layer can highlight them.
- A plain-language disclaimer block, **always present**, that states: this
  is an estimate, not proof; humanized or hand-edited text will read as
  uncertain; do not use this output as evidence in any adversarial setting.
- A timestamp and the skill version, so saved reports stay self-describing.

## 6. Fail-fast order

Sequence of checks during a single detection run. The first failure logs and
skips that signal; aggregation proceeds with whichever signals succeeded
(with a noted reduction in confidence).

1. **Input sanity.** Non-empty, at least 100 tokens (below that, all signals
   are noise; abort with a clear message). UTF-8 valid. Language detectable.
2. **Local perplexity model loads.** If the chosen small model fails to load
   (missing weights, OOM on a low-RAM machine), fall back to a smaller model
   from the same family, then to "pattern-matcher only" mode.
3. **Inverted-humanizer pattern matcher.** Pure regex / lemma matching, no
   model dependency. Always available.
4. **Burstiness and length variance.** Requires sentence tokenization; runs
   off `spaCy` or `nltk.punkt`.
5. **Stylometric analyzer.** Requires author samples; if absent, skip
   silently.
6. **Optional Claude pass.** Runs last because it is slow and quota-bound.
   Failure here downgrades to Layer 1 only with a banner in the report.
7. **Aggregate to single confidence band.** Weighted average of available
   signals; weights documented in `references/signals.md`.

## 7. Success Criteria

Boolean acceptance for the v15.3.0 tag of this skill:

- [ ] On a held-out test corpus of pure model output (Claude default, GPT
      default, Gemini default, no humanization applied), the headline band is
      `high` for at least 80 % of samples on first pass. English only is
      enough to ship.
- [ ] On a held-out corpus of text run through the ULTRON `humanizer` skill,
      the headline band degrades to `mixed` or `low` for the majority of
      samples — and the disclaimer block in the report explicitly mentions
      that humanized text is hard to detect. The goal is honesty over
      bravado: the skill must not pretend to catch what it cannot catch.
- [ ] On a corpus of clearly human text (personal blog posts, social posts,
      hand-written notes from the author's own archive), the false-positive
      rate at `high` is under 10 %.
- [ ] Spanish accuracy is at least 70 % of the English accuracy on a matched
      sample set. Lower bar acknowledged; Spanish-trained perplexity models
      are smaller and less plentiful.
- [ ] One full run on a 500-word input finishes in under 5 s on the author's
      laptop (Layer 1 only). Layer 2 adds whatever the `claude` CLI takes.
- [ ] The output report renders correctly in the Tauri Memory tab when /
      after the UI integration ships (UI integration is itself a stretch
      goal, see §11).

## 8. Rollback

The skill is fully standalone:

- It writes its report to stdout and optionally to a markdown file. No
  state changes anywhere else in ULTRON.
- It introduces no schema changes to `brain_index/index.db`, no new tables
  in any sqlite store, no new MCP server.
- Removing the skill directory (`~/.claude/skills/ai-detector/`) and the
  optional Tauri module (`src-tauri/src/ai_detector.rs`) leaves the rest of
  the system unchanged.
- If a particular signal turns out to be noisy in the wild, it can be
  disabled by setting its weight to 0 in `references/signals.md` without
  shipping new code.

## 9. Token Budget

- **Layer 1 only:** zero tokens against any subscription quota. CPU time
  only.
- **Layer 2 with Claude pass:** approximately 2 K tokens per check (one
  prompt of ~1 K input plus a ~1 K response). The skill exposes a
  `--no-deep` flag and a `layer2: false` setting so the user can cap usage
  to Layer 1 in environments where quota matters.
- **Aggregate over a typical week:** if the user runs the skill 10 times per
  day with Layer 2 on, that is ~140 K tokens / week — well inside the daily
  Claude subscription bucket.

## 10. Verification Questions

Decisions that must be answered before implementation starts. Each one has
a current bias but is not locked.

- **Which local perplexity model is the default?** Current bias: `gpt2-small`
  (~125 M params, CPU-friendly, well-studied for perplexity-based detection).
  Alternative: `distilgpt2` for faster startup on lower-end machines, or
  `phi-3-mini` if Spanish accuracy is bad. The user should confirm before
  the first weights download.
- **Inference runtime.** Current bias: Python sidecar with `transformers` +
  `torch` (CPU), invoked from the skill via the existing cockpit pattern
  (`scripts/cockpit/<name>.py`). Alternative: `candle-transformers` Rust crate
  embedded directly in the Tauri app for a self-contained binary. Rust path
  removes the Python dependency but is more work and only useful once the
  installer must run on machines without `uv`. Recommendation: Python sidecar
  in v15.3.0, evaluate Rust port for v15.4.
- **Integration mode.** Two options. (a) Standalone skill, invoked in a
  Claude Code session via natural language ("check this text for AI") — zero
  Tauri changes for the MVP. (b) Tauri-integrated, with a sidebar entry "AI
  Check" or a button in the Memory tab. Recommendation: ship (a) first, add
  (b) in the same release if time permits, otherwise defer (b) to v15.3.1.
- **Storage of analyzed texts.** Default: none. Opt-in via `--save` flag
  writes the report (not the original text) to
  `~/.ultron/.local/ai-detector/reports/<ts>.md`. Open question: should the
  original text be storable at all, given privacy and potential leakage if
  the user analyzes someone else's writing? Current bias: never store the
  original, only the derived report and offsets.
- **Pattern matcher weights.** The 29 humanizer categories are not equally
  diagnostic. Em-dash overuse is a strong signal for English; hyphenated word
  pairs are weaker in Spanish. A small held-out validation set should be
  used to fit weights once; do not let the skill self-tune at runtime.
- **Disclaimer wording.** The disclaimer block is the single most important
  output of this skill in adversarial cases. It must be reviewed by the user
  (and ideally by someone with a publishing / academic-integrity background)
  before the skill ships, because a too-confident phrasing is a real harm
  vector.

## 11. Open Questions

Items intentionally deferred to a later v15.3.x or v15.4 release.

- **Polish-level scoring.** Beyond "is this AI", a useful secondary signal
  is "is this *good* AI vs. clumsy AI". The same signals can be aggregated
  into a separate "polish" score. Defer — adds UI complexity and risks
  conflating two different questions.
- **Inline highlighting in a UI.** If the skill ships byte offsets for
  flagged spans (it should), a future Tauri view could render the input with
  hover-explained highlights, similar to a grammar checker. Defer to a UI
  pass once the skill is validated.
- **Trunk Center "review" pipeline.** A combined run that pipes a piece of
  text through `humanizer` → `ai-detector` → `grammar-check` → `style-check`
  in one pass, producing a single review report. Cross-skill orchestration
  is a larger conversation (probably v15.4) and depends on a skill-routing
  primitive that does not exist yet.
- **Watermark detection.** If Anthropic or another provider ships a public
  watermarking scheme during 2026, add a dedicated detector for that
  watermark. Until then, do not pretend the skill can find one.
- **Reverse-humanizer adversarial training.** Use the humanizer skill in a
  loop to generate adversarial examples, then re-tune the detector weights.
  Interesting research project, not v15.3.0 scope.
- **Cross-document detection.** "These five paragraphs were written by the
  same model" is a different statistical problem from "this one paragraph
  was AI". Out of scope.
- **Multilingual beyond ES/EN.** German, French, Portuguese, Japanese — all
  reasonable next targets. Out of scope for the first cut.

## Implementation hints

Not part of the spec contract — these are practical pointers for whoever
picks up the implementation, current author included.

- **Suggested file layout:**
  - `~/.claude/skills/ai-detector/SKILL.md` — the skill prompt, frontmatter
    consistent with other ULTRON L1 skills (tier, category, tags,
    `allowed-tools`).
  - `~/.claude/skills/ai-detector/references/signals.md` — the per-signal
    weights, normalization parameters, and a one-paragraph explanation of
    each signal for the curious user.
  - `~/.claude/skills/ai-detector/scripts/detect.py` — the entry point. Reads
    text from stdin / file / arg, dispatches to the signal modules, prints
    the markdown report.
  - `~/.claude/skills/ai-detector/scripts/perplexity.py` — the local-model
    perplexity computation, isolated so it can be swapped (gpt2-small →
    distilgpt2 → phi-3-mini) without touching the aggregator.
  - `~/.claude/skills/ai-detector/scripts/patterns.py` — the inverted
    humanizer pattern matcher. Should import the 29 categories from a single
    source of truth shared with `humanizer` if at all possible.
- **Suggested Rust integration (optional, v15.3.1):** a new module
  `control-center/src-tauri/src/ai_detector.rs` that shells out to
  `scripts/detect.py` via `uv run`, caches the last 50 reports in memory and
  exposes a Tauri command. Pattern is the same one used by `news.rs` and
  `memory.rs` today.
- **Suggested UI (optional, v15.3.1):** either a new sidebar entry "AI
  Check" in the Control Center, or — cheaper — a "scan this text" button on
  any text area in the Memory tab. The button posts the text to the Rust
  command above and renders the returned markdown in a drawer.
- **Estimated implementation effort:** ~2-3 days for the MVP CLI skill (one
  day for signals, one day for aggregation and report, half a day for
  Spanish coverage and the disclaimer block). ~1 week to add the Tauri
  integration and a polished UI.
- **Suggested dependencies (all subscription-only / open):**
  - `transformers` (Apache-2.0) for model loading.
  - `torch` (BSD) for CPU inference.
  - `spaCy` (MIT) for tokenization and lemmatization, with
    `en_core_web_sm` and `es_core_news_sm`.
  - `numpy` (BSD) for stylometric vectors.
  - The existing `claude` CLI (subscription) for Layer 2.
  - No GPTZero, no Originality, no Turnitin, no paid AI-detection API.
- **Prerequisite check before starting:** verify that the Python sidecar
  pattern already used by other cockpit scripts (e.g. `scripts/cockpit/
  research.py`, `scripts/cockpit/news_html_generator.py`, `scripts/cockpit/
  multimodel.py`) is the right template. If those scripts are already
  invoked from the Tauri side through `uv run`, the same wiring works for
  `detect.py`. If not, the Tauri-side launcher needs a small refactor
  before this skill can be wired into the Control Center — but the
  standalone CLI skill ships independently of that refactor.

## Honest assessment, 2026 academic landscape

For the implementer's calibration, not part of the contract:

- DetectGPT-style perplexity-curvature detectors (Mitchell et al. 2023)
  reported 0.95+ AUROC on undefended GPT-3 outputs, but the same papers
  showed accuracy collapsing toward chance once outputs were paraphrased.
  The humanizer skill is a deliberate paraphraser; expect the same collapse.
- Stylometric / Burrows' Delta methods work well at document scale (10 K+
  tokens) and poorly at paragraph scale. The skill should be honest about
  the input-length sensitivity in its disclaimer.
- Commercial detectors (GPTZero, Originality.ai) have published per-class
  precision in the 0.7-0.9 range on their own benchmarks; independent
  replications (Sadasivan et al. 2023, Liang et al. 2023) find they
  systematically false-positive on non-native-English writers. The MVP must
  not reproduce that bias; the disclaimer should warn explicitly.
- Watermarking schemes (Aaronson, Kirchenbauer, etc.) only work when the
  generating model cooperates. As of this spec, no public consumer model
  ships a watermark the user can rely on. The skill therefore deliberately
  does not include a watermark-detection signal — there is nothing to
  detect.

The net of all this: a careful multi-signal local detector with an honest
output band is a useful self-check tool. It is not a courtroom instrument
and the spec must not let it become one.

# ULTRON Roadmap v14.2 → v15.0

> Sprint Genesis-14.1 + ULTRA polish entregó 13 commits y dejó el sistema
> ship-ready. Este roadmap define los siguientes 4 sprints temáticos.
> Cada uno es ~1 semana de trabajo. Total: ~1 mes.

## Filosofía global

- **No custom ML training.** Modelos pre-entrenados aplicados quirúrgicamente.
- **Token reduction es la métrica madre.** Todo cambio se justifica por
  ahorro de tokens / sesión o mejora de retrieval.
- **Self-improving sin auto-apply.** Cualquier loop de auto-mejora SIEMPRE
  pasa por revisión humana antes de aplicar (anti-laundering).
- **Web pública es el último sprint.** Necesita el sistema cerrado y
  presentable; no hay punto en venderlo si todavía está cambiando.

## v14.2 — "TOKEN HUNTER" (sprint ~1 semana)

**Objetivo:** reducir tokens por sesión "a lo bestia". Target ambicioso:
**-50% del baseline actual** (medido en context.md + system prompt + skill
listings + MEMORY.md).

### Phase 0 — Baseline + research (1 día)

- Medir hoy: total tokens al SessionStart (context.md + MEMORY.md +
  CLAUDE.md global + harness skill listing). Anclar.
- WebSearch: state-of-the-art 2026 en token reduction para agentes:
  - Anthropic prompt caching cookbook (cache hit rate optimization)
  - Context compression (semantic summarization vs LLMLingua-style)
  - Skill description elision (Claude Code's `skillListingBudgetFraction`)
  - Lazy loading de personas (no load until activated)
  - Tool description trimming
- Output: `~/.ultron/audits/token-research-2026-05-XX.md`

### Phase 1 — Prompt caching audit (1 día)

- Verificar que el SystemPrompt de cada hook respeta cache breakpoints
- Medir cache hit rate actual con `ultron doctor --token-audit`
- Reorganizar bloques estables al inicio (cacheable) y volátiles al final

### Phase 2 — Skill listing radical (2 días)

- Implementar lazy-loading: harness sólo lista nombres + 1-líneas; las
  descripciones completas se cargan on-demand cuando el dispatcher
  evalúa la skill como candidata.
- Refactor del `intent-dispatcher` para hacer dos passes: nombre→shortlist,
  shortlist→full descriptions.
- Esperado: -34k tokens / sesión sólo en este eje.

### Phase 3 — MEMORY.md compresión (1 día)

- Detectar redundancia entre MEMORY.md, context.md y CLAUDE.md global
- Aplicar política "single source of truth": cada hecho vive en EXACTAMENTE
  un sitio, los demás referencian
- Tool: `ultron memory dedupe --dry-run` (nuevo)

### Phase 4 — Tool description trimming (1 día)

- Auditar las descripciones de tools (Read, Edit, Bash, etc.) — algunos
  tienen 200+ tokens de overhead. Si son obvias, trimear.
- Cuidado: las descriptions ENSEÑAN al modelo cómo usar la tool.

### Phase 5 — Smoke + commit (resto)

- Volver a medir el baseline. Confirm -50%.
- Doctor: nuevo detector D19_TOKEN_REGRESSION que warns si subes >+5%
  vs el snapshot post-Phase 5.

**Riesgo principal:** trimear demasiado degrada calidad de respuestas.
Mitigación: A/B con un set de queries doradas antes de mergear.

## v14.3 — "META-PROMPTER" (sprint ~1 semana)

**Objetivo:** prompts que se auto-mejoran por feedback. Sin training. Sólo
prompts-sobre-prompts y un loop humano-en-el-medio.

### Phase 0 — Selección del corpus de prompts a optimizar

- Los 9 Kirkardo + 6 skills clipboard prompts (15 prompts ya estructurados)
- Tabla scorecard: tokens, golden-output similarity, user-satisfaction
  (manual rating)

### Phase 1 — Meta-prompt template

- Patrón Anthropic: meta-prompt que recibe (prompt, ejemplos buenos,
  ejemplos malos) y devuelve prompt mejorado.
- Implementar como skill: `prompt-improver`.
- Wire al TUI: botón "✎ Mejorar este prompt" en cada Kirkardo audit row.

### Phase 2 — Loop semi-automático

- Después de N usos, recoger los outputs reales y los implícitos (¿el
  usuario re-prompted? ¿editó el resultado?)
- Generar versión candidata del prompt
- Surfacear diff al usuario para approve/reject (anti-laundering)

### Phase 3 — Versionado

- Cada prompt vive con un campo `iteration: N` y `superseded_by: <ref>`
  en frontmatter
- Doctor detector D20_PROMPT_DRIFT: avisa si una iteration N tiene
  scorecard peor que N-1

### Phase 4 — Self-eval skill

- Una skill `prompt-eval` que toma (prompt, output) y devuelve un
  scorecard 0-10 sobre dimensiones (precisión, conciencia, formato,
  completitud)
- Loop: prompt → output → eval → si bajo, generar variante → comparar

**No-goals explícitos:** no entrenar nada. No fine-tuning. No RLHF.
Sólo prompts + Claude/Codex/Gemini juzgando outputs.

## v14.4 — "PERFECT MEMORY" (sprint ~1-2 semanas)

**Objetivo:** memoria semántica completa sobre el vault. Cuando recuerdas
el concepto pero no las palabras exactas, el sistema te trae la nota.

### Phase 0 — Qdrant install

- Path A (Docker local) o Path B (Cloud) — ya documentado en
  `~/.ultron/plans/qdrant-mcp-install-steps.md`.
- Esto debe estar hecho ANTES de v14.4. Es bloqueante.

### Phase 1 — Embedding pipeline

- Para cada nota del vault (538 notas, ~10k chunks), calcular embedding
  con `sentence-transformers/all-MiniLM-L6-v2` (local, gratis, 384 dim)
  O `text-embedding-3-small` (OpenAI, paid, 1536 dim).
- Decision pendiente: local vs API. Recomendación: local.
- Push a Qdrant collection `ultron_vault`.

### Phase 1.5 — Embedding pipeline para `routing.jsonl`

- También indexar las queries de routing.jsonl. Permite "queries similares
  a esta" y empezar a aprender patrones.

### Phase 2 — Hybrid search

- Nueva tool `brain_index hybrid <query>`: combina FTS5 (keyword) +
  Qdrant (semantic) con reciprocal rank fusion.
- Si una query devuelve resultados parecidos en ambos → alta confianza.
- Si sólo semantic → "puede ser esto".
- Si sólo FTS5 → "match literal pero no conceptual".

### Phase 3 — Auto-recall en SessionStart

- L0 context.md ahora incluye top-3 notas semánticamente cercanas a la
  última query de la sesión anterior.
- Permite "wake-up" más informado sin gastar tokens en repreguntar.

### Phase 4 — `intent-dispatcher` con embeddings

- Reemplazar (o complementar) la regex-based del dispatcher con una
  semantic-similarity vs el corpus de routing.jsonl etiquetado.
- 1000s de samples ya hay. Train un k-NN simple. 50 LOC.

### Phase 5 — Doctor + tests

- D21_VAULT_INDEX_DRIFT: avisa si vault tiene N notas y Qdrant tiene M ≠ N.
- Tests: golden retrieval set (50 queries con respuesta esperada).

**Riesgo principal:** embedding model drift cuando cambias de versión.
Mitigación: pin model name en config + reindex script.

## Lo que NO está en este roadmap (intencionalmente)

- Custom ML training / fine-tuning. Trampa de tiempo.
- RL para tuning del sistema. Reward sparse.
- Convertir ULTRON en SaaS. Si surge, es un proyecto separado.
- Mobile app. La TUI + claude.ai es suficiente para uso personal.
- Multi-user. ULTRON es single-user por diseño.

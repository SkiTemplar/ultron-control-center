# Control Center 2.0 — Kirkardo UX Rubric

**Fecha:** 2026-05-23
**Target:** promedio >= 9.5 / 10 antes del tag `v2.0.0`.
**Auditor:** Kirkardo (profesor estricto) — manual walkthrough o subagente.

Esta rubrica es el gate final del rewrite 2.0. Cada criterio se puntua 1-10. Cualquier fallo de scope <30min se arregla inline; lo demas pasa a issues post-v2.0.

---

## Criterio 1 — First-launch onboarding completes without error (peso x1)

**Que mide:** que un usuario que arranca la app por primera vez (con `~/.ultron/` recien creado, sin `projects.json`, sin `kanban.json`) llega al Dashboard sin crashes.

**Como verificar:**
1. Renombrar temporalmente `~/.ultron/` a `~/.ultron.bak/`.
2. Crear un `~/.ultron/` vacio.
3. `cd control-center && npm run tauri dev`.
4. Verificar: no aparece toast de error, el sidebar arranca en "Projects", el panel central muestra empty state con CTA "Add project".
5. Restaurar: `rm -rf ~/.ultron && mv ~/.ultron.bak ~/.ultron`.

**Puntuacion:**
- 10: completa sin warnings en consola.
- 7: completa pero con warnings de migracion.
- 4: crash bloqueante o pantalla en blanco >3s.
- 1: no arranca.

---

## Criterio 2 — Default tab Projects loads in <500ms perceived (peso x1)

**Que mide:** time-to-first-paint del tab Projects desde click en Sidebar.

**Como verificar:**
1. App ya arrancada en otro tab (e.g. System).
2. Abrir DevTools del webview (`Ctrl+Shift+I`).
3. Pestana Performance -> Record.
4. Click en "Projects" en el sidebar.
5. Stop record cuando el Kanban global este renderizado.
6. Medir desde el `mousedown` hasta el ultimo paint.

**Puntuacion:**
- 10: <300ms.
- 9: 300-500ms.
- 7: 500-800ms.
- 4: 800ms-2s.
- 1: >2s o no renderiza.

## Criterio 3 — Opening a project as a tab <300ms perceived (peso x1)

**Que mide:** click en una card de proyecto -> aparece la nueva pestana de proyecto + ProjectWorkspace renderizado.

**Como verificar:**
1. Con la app abierta en tab Projects.
2. DevTools -> Performance -> Record.
3. Doble-click en una card de proyecto.
4. Stop cuando el sub-tab "Board" del proyecto este renderizado.
5. Medir desde mousedown hasta ultimo paint.

**Puntuacion:**
- 10: <200ms.
- 9: 200-300ms.
- 7: 300-600ms.
- 4: 600ms-1.5s.
- 1: >1.5s.

## Criterio 4 — Kanban DnD responsive (frame budget <16ms during drag, peso x2)

**Que mide:** que mover una card de Backlog -> In Progress sea fluido. No debe haber frame drops detectables.

**Como verificar:**
1. Abrir un proyecto con al menos 6 cards en distintas columnas.
2. DevTools -> Performance -> Record.
3. Arrastrar una card de Backlog a In Progress.
4. Stop cuando la card aterrice.
5. Verificar: ninguna barra roja >16ms en el track de frames. La card se ve siempre bajo el cursor (no se queda atras).

**Puntuacion:**
- 10: 60fps constante, cero frames >16ms.
- 8: max 2 frames >16ms.
- 5: frame drops visibles pero la card no se desincroniza.
- 2: la card se desincroniza del cursor.
- 1: drag no funciona.

## Criterio 5 — EmbeddedTerminal renders Claude output legibly (peso x1)

**Que mide:** que el `xterm.js` embebido renderice el output de `claude` con el theme oscuro de la app, sin wrapping erroneo, sin caracteres rotos, sin escape codes visibles.

**Como verificar:**
1. Abrir un proyecto -> dispatch de una card que invoque `claude`.
2. Esperar a que aparezca el welcome banner de Claude.
3. Verificar:
   - Colores ANSI matchean theme dark de la app.
   - No hay caracteres ESC visibles (e.g. `^[[1m`).
   - Texto largo se wrapea al ancho de la terminal (no overflow horizontal).
   - El cursor parpadea.

**Puntuacion:**
- 10: indistinguible de Windows Terminal.
- 8: minor color mismatches.
- 5: wrapping erroneo o caracteres rotos ocasionales.
- 2: escape codes visibles.
- 1: no renderiza.

## Criterio 6 — Mem0 status indicator updates within 2s (peso x1)

**Que mide:** la pestana Memory muestra "Connected" en <=2s tras un test exitoso, "Disconnected" en <=5s tras kill del MCP.

**Como verificar:**
1. Tab Memory.
2. Click "Test connection" -> medir tiempo hasta el badge "Connected".
3. Borrar la API key de `~/.claude/settings.json` (con backup).
4. Click "Test connection" de nuevo -> medir tiempo hasta "Disconnected".
5. Restaurar la API key.

**Puntuacion:**
- 10: ambos <2s.
- 8: connected <2s, disconnected <5s.
- 5: connected 2-5s.
- 2: no actualiza sin recargar.
- 1: indicador muerto.

---

## Criterio 7 — All sidebar tabs render without crash with empty state (peso x1)

**Que mide:** que cada top-level tab del sidebar tenga un empty state usable (no spinner infinito, no error boundary, no pantalla en blanco).

**Como verificar:**
1. Renombrar temporalmente `~/.ultron/` y `~/.claude/projects/` a `.bak`.
2. Crear `~/.ultron/` vacio.
3. Arrancar app. Click en cada tab uno por uno:
   - Dashboard
   - Projects
   - Skills
   - Agents
   - Memory
   - Sessions
   - System
   - Settings
4. Verificar: cada uno muestra contenido (empty state, lista vacia con CTA, o panel funcional). Cero crashes.
5. Restaurar.

**Puntuacion:**
- 10: 8/8 ok con CTA visible.
- 8: 8/8 ok pero algun empty state pobre.
- 5: 6-7 ok, 1-2 con spinner colgante.
- 2: 1-2 crashes.
- 1: 3+ crashes.

## Criterio 8 — settings.json editor saves atomically with backup confirmation (peso x1)

**Que mide:** que editar `~/.claude/settings.json` desde el panel "settings.json" lo guarde de forma atomica (sin corromper el file si hay error JSON) y muestre toast de confirmacion.

**Como verificar:**
1. Tab Settings -> primera pestana "settings.json".
2. Editar un campo trivial (e.g. anadir un comentario nuevo en `general.something`).
3. Save.
4. Verificar:
   - Toast "Saved" aparece en <1s.
   - El fichero en disco refleja el cambio.
   - Si introduzco JSON malformado y guardo, el editor muestra error inline + el fichero original SIGUE intacto.

**Puntuacion:**
- 10: atomico + toast + JSON malformado bloqueado.
- 8: atomico + toast, malformado bloqueado pero sin mensaje claro.
- 5: guarda pero sin atomicidad (file corruptible).
- 2: no guarda.
- 1: crash.

## Criterio 9 — PC Diagnostic runs in <5s (peso x1)

**Que mide:** click "Run diagnostic" -> reporte completo renderizado en <5s.

**Como verificar:**
1. Tab System -> sub-tab Diagnostics.
2. Cronometrar desde click "Run diagnostic" hasta que las 6 cards (System, Disks, Network, App, Top procs, Event log) esten visibles.

**Puntuacion:**
- 10: <3s.
- 9: 3-5s.
- 7: 5-8s.
- 4: 8-15s.
- 1: >15s o cuelga.

---

## Criterio 10 — GitHub Library search returns results in <3s (peso x1)

**Que mide:** click "Search GitHub" en tab Agents -> escribir un query -> debounce 500ms + `gh search code` -> resultados visibles.

**Como verificar:**
1. Tab Agents -> "Search GitHub".
2. Escribir `code-review`.
3. Cronometrar desde el ultimo keystroke hasta los primeros resultados renderizados.

**Puntuacion:**
- 10: <2s.
- 9: 2-3s.
- 7: 3-5s.
- 4: 5-10s.
- 1: >10s o timeout.

Cómo funciona ULTRON de verdad

Esta página describe el sistema tal y como está construido y medido, incluida la lista de cosas que se probaron y no funcionaron. Cada afirmación de esta página tiene detrás un test, un benchmark o un evento auditable en el ledger. Si algo de aquí deja de ser cierto, es un bug de documentación.

01 · Memoria — el write-path gobernado

La memoria persistente vive en brain.db (SQLite + FTS5), la única fuente de verdad, con un escritor único: MemoryService. Nada más escribe memoria. El recall denso lo sirve un Qdrant nativo con embeddings E5-large (1024d, prefijos query:/passage:).

Nada entra directo. Toda captura (hooks de sesión, resultados de subagentes, decisiones detectadas) se propone como candidato y atraviesa esta cadena antes de ser memoria:

hook / agente
   │  candidato (JSON por stdin → sidecar ultron-memory)
   ▼
[gate de informatividad]   un fallo sin sustancia ("tool exit code 1" a secas) no se propone
[redacción de secretos]    ghp_/sk-/AKIA/… fuera antes de tocar disco
[redacción + gate PII]     email/teléfono/rutas de usuario → item marcado Secret (fuera de recall)
[dedupe exacto BLOQUEANTE] twin con mismo content_hash (activo o pendiente, mismo scope+proyecto)
                           → no-op + evento; el CLI responde {skipped:"duplicate"}
[detector de contradicción] vecinos densos + juez conservador; conflicto → cuarentena humana;
                           state-update 1:1 claro (opt-in) → supersede enlazado
   ▼
inbox humano  ──o──  auto-approve por bandas (≥umbral → activo · medio → pendiente · ruido → rechazado)
   ▼
brain.db (evento auditable por cada transición; forget = borrado duro para PII,
deprecate --id = retirada RECUPERABLE para hechos de eras muertas)

2026-07-02: se purgaron 121 falsos positivos ("Error en WebFetch: tool exit code 200" — un bug leía el status HTTP como exit code), 1.782 duplicados exactos (582 grupos) y 16 afirmaciones de eras muertas. El corpus pasó de 5.593 a ~3.670 items activos y el dedupe ahora bloquea en el write-path.

02 · Recall — el read-path con gates

Una consulta pasa por recuperación híbrida y una cadena de gates hasta convertirse en un pack compacto (k=8, ≤1500 tokens) que se inyecta como contexto. Cada descarte lleva su razón (el subcomando trace expone el pipeline completo, headless):

query
  ├─ denso:  E5 → Qdrant top-30 (cosine)          ├─ sparse: FTS5/BM25 top-30
  ▼
RRF (k=60, fusión ponderable) + re-rank de calidad (confianza × recency) + tie-break por cosine e id
  ▼  por candidato, en orden:
[status=active] [sin codebase_fact] [vigencia temporal + TTL] [filtro de proyecto (ambiente aplica)]
[gate vault] [sensitivity ≠ Secret] [TRUST GATE anti-inyección: "ignore previous", "[system]"… → cuarentena]
[cola BM25 sin respaldo denso → fuera] [clamp 180 tokens/entrada: un resumen gordo no desaloja a nadie]
  ▼  sobre el pack completo:
[score-floor 0.83: sin dense ≥ floor NI sparse fuerte → pack VACÍO (abstiene)]
[TRUST GATE de cobertura: término informativo con 0 documentos en el corpus → abstiene
 ("¿cuándo se desplegó en AWS?" → el corpus no conoce "AWS" → no se inyectan vecinos temáticos)]

La filosofía: abstenerse es mejor que inyectar relleno. Un pack vacío se declara (abstained: true + warning), nunca en silencio.

03 · Medición — tres jueces y decisiones con evidencia

Ninguna mejora del retrieval se acepta si no mejora (o al menos no daña) a tres jueces independientes:

JuezQué mideEstado 2026-07-02
memory-benchBenchmark adversarial externo: temporal, stale, multi-hop, contradicciones, secretos, cross-project, abstain (near-misses incluidos), + invariantes de inyección/secretos/gobernanza en cada query9.94/10
eval-fullGolden set etiquetado a mano (ranking-quality, recall@8/nDCG/waste)recall@8 0.712
eval --goldenOráculo de labels independiente (29 queries, no circular)recall@8 0.682

Y el sistema entero se audita con el harness Kirkardo (22 categorías, checks binarios reproducibles) y doctor (SQLite/Qdrant/reconcile/evals/binario fresco).

Lo que se probó y NO entró (esto también es el manual)

  • Reranker cross-encoder (BGE-v2-m3): −4.6pp de recall y 3× de latencia → ULTRON_RERANK queda OFF.
  • Fanout 50 / RRF k=20: ganaba en un juez, perdía en los otros dos (sobreajuste cazado) → defaults 30/60.
  • Pesar denso > sparse: expulsa del top-8 a los relevantes que solo llegan por match léxico → peso 1.0.
  • Gate de diversidad del pack (MMR-lite): los golden premian redundancia; queda opt-in hasta tener un juez de información-por-token.

Un "no" medido vale tanto como un "sí": impide comprar mejoras falsas. Los cuatro quedaron como knobs de entorno para futuros A/B.

04 · Hooks — la sesión viva

Claude Code expone ~30 tipos de hook; ULTRON usa ~9, elegidos por valor y no por coleccionismo:

HookQué hace
SessionStartResume fiel: nota viva del harness, tareas abiertas del kanban, contexto del proyecto, salud de Qdrant
UserPromptSubmitOrchestrate: encuadre por intención, agentes candidatos, memorias relevantes (pack gobernado), directiva de delegación
PostToolUse(+Failure)Captura de errores CON contexto (qué se intentó + qué falló) y gate de informatividad
StopCompresión de sesión, drenaje de decisiones, cola Run Batch de comandos rechazados/fallidos
SubagentStopHarvest de resultados de subagentes con atribución (agente, label, proyecto)
PreCompactPreserva hechos clave L0 antes de compactar el contexto

Todos los hooks son no-op-safe (un hook roto jamás bloquea la sesión), con checksums en un manifest versionado cuya paridad se verifica en pre-commit, y selftests conductuales por hook.

05 · Skills — routing lazy

El catálogo de skills vive desactivado (.disabled) y no cuesta tokens. Un núcleo mínimo está siempre activo; el resto lo inyecta on-demand el dispatcher según el prompt:

  • v2 determinista: triggers léxicos con frases (no substrings — "arr" → "arregla" fue una lección cara), accuracy@3 medida en harness.
  • v3 semántico: fallback por similitud de embeddings cuando lo léxico no matchea, servido por el daemon E5 residente.

Los harnesses _verify_final y _accuracy_at3 deben quedar verdes tras tocar el routing. Conservar skills es gratis; activarlas en masa no.

06 · Orquestación — AI Router

route(zone, prompt) camina una cadena primary→fallback por zona: groq como primary y gemini cloud de fallback en zonas generales; CLI-first (codex-cli) en zonas de código; ollama para lo offline. La métrica honesta es real_fallback_rate sobre ventana viva — no la tasa acumulada de intentos.

Alcance declarado: el router rutea las llamadas de la app Tauri. NO rutea el CLI de Claude Code, que habla directo con Anthropic. gemini-CLI murió el 2026-06-19 (Google cortó el free-tier OAuth) y fue erradicado; gemini cloud sigue vivo como fallback.

07 · Interfaz — Control Center

App de escritorio (Tauri 2 + React 19). Las superficies que consumen todo lo anterior:

  • Memory: inbox de candidatos (aprobar/editar/rechazar, auto-approve por bandas) + browser del corpus gobernado.
  • Retrieval Inspector: el trace del recall — por qué entró cada memoria y por qué se descartó cada descartada.
  • Monitor: sesiones vivas, subagentes en curso, delegaciones y telemetría de routing.
  • Skills / Agents / Library: catálogo con toggle lazy, edición con lint, instalación con captura post-install.
  • Kanban: estado por proyecto, editado por CLI (scripts/kanban.mjs), con recordatorio automático al cerrar tareas.
